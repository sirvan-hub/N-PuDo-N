## 1. Executive result

**Readiness verdict: BLOCKED for direct migration; READY for schema-contract design.**

The current NestJS backend uses SQLite, TypeORM automatic schema synchronization, and five entity classes. The canonical SQL migration defines twelve tables plus constraints, indexes, triggers, and an initial administrator seed. Application services and DTOs reveal mismatches beyond column names: registration/login uses username + password, the pricing implementation conflicts with the approved blueprint, and the old test plan describes endpoints and OTP behavior that do not match current controllers.

Do not execute 001_initial_schema.sql against any durable database as-is. The first migration must follow an agreed contract, not blindly choose either current entities or legacy SQL.

## 5. Cross-cutting findings

### P0 — Resolve before production migration

1. Parcel status incompatibility: code writes PENDING_APPROVAL; canonical CHECK excludes it.
2. Invoice service reads parcel.recipient_id and parcel.current_hub_id, neither declared on ParcelEntity.
3. Wallet accounting lacks ledger and atomicity.
4. Pricing implementation conflicts with approved blueprint. Current code: 30% through 12h, 70% through 36h, then +60% per started 48h, expiry at 120h. Blueprint: under 12h 20%, 12–24h 40%, then +50% per started additional 24h, expiry at 168h. Exact boundaries and timezone semantics need tests.
5. TypeORM synchronize:true must be disabled for durable production and replaced by versioned migrations.
6. Default administrator seed in canonical SQL is not safe for deployment.

### P1 — Resolve before claiming the workflow is end-to-end

7. Test-plan drift: legacy plan describes phone/OTP login; current DTO/service use username/password and verifyOtp throws GoneException. Refresh plan or implement intended OTP contract.
8. Hub creation accepts any DTO; DB constraints alone are insufficient API validation.
9. Hub nearby ignores coordinates/radius and returns distance 0.
10. Parcel DTO requires proposed_hub_id while entity marks it nullable.
11. Timestamp-based invoice numbers can collide under concurrency.
12. No automated current-backend entity/service test paths were found in the repository tree. CI currently installs dependencies and builds; it does not prove migration or database integration correctness.
13. backend/test-flow.ps1 attempts unauthenticated parcel creation, while current controller requires JWT and COURIER role. Replace or mark obsolete.

## 6. Proposed target contract and migration order

Proposal for review; nothing applied.

### Migration 0001 — PostgreSQL baseline
- Create only agreed target tables, types and constraints.
- Use UUID keys, explicit FK behavior, timestamptz, numeric money types and deliberate indexes.
- Disable synchronize for durable environments; use versioned migrations.
- Do not seed default administrator credentials.
- Use migration history and fail startup clearly on migration failure.

### Migration 0002 — identity/roles
- Preserve username/password_hash unless auth contract is formally redesigned.
- Normalize and validate phone/role/national ID.
- Enforce uniqueness and required fields only after null/duplicate scans.
- Bootstrap administrator separately and securely.

### Migration 0003 — parcel state/custody
- Agree state values against master blueprint and state-machine baseline.
- Add FK relations and event timestamps without duplicate sources of truth.
- Add registration/custody records with actor, time and idempotency metadata.
- Test valid/invalid transitions before strict status CHECK constraints.

### Migration 0004 — tariff/invoices
- Align rates and expiry with approved blueprint.
- Test 11:59:59, 12:00:00, 23:59:59, 24:00:00, every additional 24-hour boundary and 168-hour expiry.
- Define percentage units and invoice tariff snapshot.
- Resolve missing recipient/current-hub identifiers.
- Generate invoice numbers collision-safely.

### Migration 0005 — wallets/ledger/settlement/audit
- Add ledger and settlement entities/tables, immutable references, idempotency constraints and atomic balance posting.
- Establish successful-payment/refund/settlement/payout uniqueness rules.
- Audit custody, financial and privileged actions.
- Do not enable real money movement until integration tests pass.

### Migration 0006 — optional integrations
- Device tokens only when push integration is in scope.
- Spatial columns/indexes only after the location model is approved.

## 7. Data preservation and migration controls

Before writing or running a migration:
1. Back up backend/dev.db securely outside public Git and restrict access.
2. Determine whether it contains personal/real data without printing record contents in logs.
3. Inventory table names, columns, row counts, nulls, duplicates, invalid statuses, orphan FKs, invalid JSON, monetary maxima and timestamp ranges.
4. Rehearse export/import against disposable PostgreSQL.
5. Compare row counts and deterministic checksums/aggregates per table.
6. Run application contract and negative authorization tests against PostgreSQL.
7. Prepare a restore-based rollback; do not rely on destructive reverse migrations for recovery.
8. Only after rehearsal passes, consider an isolated Render test service and separate test database. Leave the old service untouched until explicit authorization.
